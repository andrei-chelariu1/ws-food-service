# `migrations/` — Alembic Schema Migrations

The Flyway/Liquibase equivalent. Every schema change lives here as a reviewable,
version-controlled, reversible Python file.

```
migrations/
├── env.py                        async, single-driver; imports EVERY module's models
├── script.py.mako                template — includes the pre-commit checklist
└── versions/
    ├── 0001_initial_schema.py    handwritten: 4 tables, constraints, indexes
    └── 0002_seed_admin.py        idempotent data migration
```

---

## Daily commands

```bash
make migrate                        # alembic upgrade head
make current                        # which revision is applied?
make history                        # full history
make downgrade                      # roll back exactly one
make revision m="add x to y"        # autogenerate a new revision
```

Without Docker: `alembic upgrade head` (needs `DATABASE_URL` set).

---

## `env.py` imports every module's models — this is load-bearing

`Base.metadata` is populated as a **side effect** of importing model classes. Alembic compares
that metadata against the live database.

**Miss an import and autogenerate will emit `DROP TABLE donations`**, because from its point of
view that table exists in the database and not in the code.

So: **adding a module means adding a line to the import block in `env.py`.** It is also the one
place where the otherwise-independent feature modules necessarily meet — one physical database,
one migration history. A deliberate, documented coupling point; see `app/shared/db/base.py`.

## Rules

### 1. Never edit a migration that has been applied anywhere

Alembic records the revision id, not the file contents. Editing an applied revision means your
database and everyone else's silently diverge, with no error and no way to detect it. Write a
new migration instead — always.

### 2. Always read an autogenerated migration before committing it

Autogenerate is a **first draft**. The checklist is in `script.py.mako`, so it appears at the
top of every generated file:

1. Does `downgrade()` actually reverse `upgrade()`? Autogenerate often gets this wrong or
   leaves it empty. An irreversible migration means an irreversible deploy.
2. Is a new NOT NULL column on an existing table given a `server_default`, or backfilled?
   Otherwise it fails the moment the table has rows.
3. Does an index on a large table use `postgresql_concurrently=True`? A plain `CREATE INDEX`
   holds an exclusive lock for its duration — minutes of downtime on a big table.
4. Was a column rename emitted as drop + add? **That destroys the data.** Replace with
   `op.alter_column(..., new_column_name=...)`.
5. Are constraint names present? They should be, thanks to `naming_convention` — a missing one
   means something bypassed the declarative base.

### 3. Test the rollback

```bash
make migrate && make downgrade && make migrate
```

A migration you have never rolled back is a migration you cannot roll back.

### 4. Migrations pin the schema; models track the present

**Never use the ORM in a migration.** If `User` later gains a column, an ORM-based insert would
emit SQL referencing a column that does not exist yet when the migration runs on a fresh
database. `0002_seed_admin.py` uses raw parameterised SQL for exactly this reason.

The one exception is importing a *pure function* — `0002` imports `BcryptPasswordHasher` so the
seeded hash is produced by the same code path as a real registration. A hardcoded hash literal
would work until someone changed the algorithm, at which point the seeded admin would silently
stop being able to log in.

## The naming-convention gotcha (this one bit us)

`app/shared/db/base.py` defines `ck_%(table_name)s_%(constraint_name)s`, and **Alembic applies
that convention to its own operations too**. So in a migration:

```python
sa.CheckConstraint("...", name="status_valid")  # -> ck_donations_status_valid   ✓
sa.CheckConstraint(
    "...", name="ck_donations_status_valid"
)  # -> ck_donations_ck_donations_status_valid  ✗
```

PK, FK and index patterns do **not** reference `%(constraint_name)s`, so those are spelled out
in full (`name="pk_users"`, `name="fk_food_items_owner_id_users"`).

Found by applying `0001` to a real Postgres and reading `pg_constraint` — the SQLite test suite
cannot catch it, because SQLite reports constraints differently.

## Why the first migration is handwritten

Autogenerate would produce something close, but:

* it emits tables in arbitrary order, which fails when a foreign key precedes its target;
* it does not create the `pgcrypto` extension that `gen_random_uuid()` needs;
* it produces an empty or wrong `downgrade()` more often than not;
* partial indexes (`postgresql_where`) are frequently mis-rendered.

The first migration establishes the shape of the whole schema, so it is worth writing
deliberately. Subsequent ones can start from autogenerate, with the checklist applied.

`downgrade()` drops tables in **reverse** dependency order — notifications, donations,
food_items, users — which is the property that makes the rollback work. It leaves `pgcrypto` in
place: other schemas may rely on it, and dropping a shared extension during a rollback is how a
rollback becomes an incident.

## Why seeding is a migration

A fresh database with no admin is unusable — there is no way to promote anyone, because
promotion requires an admin. So the first admin must be created by something that is not the
API.

As a migration it runs automatically wherever migrations run: a laptop, CI, staging,
production. A separate `seed.py` is something someone must remember, and the failure mode is a
deploy that completes "successfully" into an unusable system.

`0002` uses `INSERT ... WHERE NOT EXISTS`, so it is safe against a database that already has
the admin (a re-run, a restored backup, a stamped-then-upgraded history).

> **The seed email must be one `EmailStr` accepts.** `admin@foodwaste.local` inserts fine and
> then **cannot log in** — email-validator rejects special-use TLDs, so the login endpoint's own
> validation returns 422. The default is `admin@foodwaste.example`, and
> `tests/shared/test_config.py::test_seed_admin_email_is_accepted_by_the_login_schema` pins it.
> Found by actually logging in as the seeded admin.

## Async `env.py` — a deviation from ARCHITECTURE.md

ARCHITECTURE.md lists `psycopg2-binary` so Alembic can run synchronously: two drivers, two
connection URLs, two ways for the connection string to be wrong.

Alembic supports async natively via `connection.run_sync`, so we use one driver (`asyncpg`) and
one URL. `alembic.ini` leaves `sqlalchemy.url` empty on purpose — `env.py` reads it from
`Settings`, so the connection string lives in one place and no credentials sit in a committed
file. See `docs/adr/0003-async-alembic-single-driver.md`.

## Migrations run in the entrypoint, not in the app lifespan

`scripts/entrypoint.sh` runs `alembic upgrade head` **before** uvicorn binds a port.

Running them in `lifespan` looks convenient, but with N replicas all N race to migrate on every
deploy. Alembic takes an advisory lock so they cannot corrupt each other, but N-1 replicas then
block until the leader finishes — and a slow migration means a failed startup probe and a
restart loop.

**For real production**, promote migrations to a separate pre-deploy job (Kubernetes Job, ECS
task, CI step) that must succeed before new pods roll out. Doing it in the entrypoint is the
right trade for a sample and for small deployments; it *is* a trade.
