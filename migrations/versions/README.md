# `migrations/versions/` — the revision files

## Purpose

The ordered, append-only history of the schema. Each file is one revision, linked to its parent by
`down_revision`, forming a chain Alembic walks.

## What belongs here

| ✅ | ❌ |
|---|---|
| DDL: tables, columns, indexes, constraints | application logic |
| Small, **idempotent** data migrations (see `0002`) | imports of `app.modules.*` models |
| An `upgrade()` **and** a working `downgrade()` | anything that reads `Settings` at import time |

## The one rule that matters

> **Never edit a revision that has been applied anywhere but your own laptop.**

Alembic records only the revision **id** in `alembic_version` — not its contents. Editing an
applied file leaves every database that already ran the old version permanently, silently
inconsistent with the file that claims to describe it. There is no error; there is just a schema
that disagrees with its history.

To change something already applied: **add a new revision.**

## Why the files are handwritten here

`0001_initial_schema.py` was written by hand rather than autogenerated. Autogenerate is excellent
for incremental changes and produces an unreviewed wall of code for an initial schema — and it is
the initial schema whose index and constraint choices deserve the most scrutiny. For everything
after this, use `make revision m="..."` and then **read the diff**.

## Why `0001` is plain SQL, not `op.create_table(...)`

`0001_initial_schema.py`'s `upgrade()`/`downgrade()` contain **only `op.execute("<SQL>")` calls** —
`CREATE EXTENSION`, `CREATE TABLE`, `CREATE INDEX`, verbatim. No `sa.Column`, no
`op.create_index`, no SQLAlchemy construct that generates DDL for you. Same idea `0002_seed_admin.py`
already uses for its `INSERT`: what runs against the database should be readable *as SQL*, copy-
pasteable straight into `psql`, by anyone who knows SQL and nothing about Alembic's Python API.

One consequence worth knowing: because raw SQL bypasses `naming_convention` entirely, every
constraint in `0001` is spelled out in full (`CONSTRAINT ck_users_role_valid CHECK (...)`) rather
than relying on Alembic to expand a short name — see the note below, which still applies to any
*Python-style* revision (like `0002`) that uses `sa.CheckConstraint`.

## ⚠ Use SHORT constraint names in migration files

```python
sa.CheckConstraint("status IN (...)", name="status_valid")     # ✅
sa.CheckConstraint("status IN (...)", name="ck_donations_status_valid")   # ❌ doubles
```

Alembic applies the `naming_convention` from `app/shared/db/base.py` to its *own* operations too.
Pass an already-conventional name and you get it twice:

```
ck_donations_ck_donations_status_valid
```

Observed in `pg_constraint`, not guessed. The generated name is what a later
`drop_constraint` will look for, so a doubled name means a `downgrade()` that cannot find its own
constraint.

## Why imports here are restricted

`0002_seed_admin.py` imports `BcryptPasswordHasher` — a **pure function** with no database
dependency — and writes with raw parameterised SQL rather than the ORM.

Importing models would couple the revision to the *current* model definition. A migration must
describe the schema **as it was at that revision**; if `User` gains a NOT NULL column tomorrow, a
model-based revision from last month starts failing on a fresh database. Raw SQL is frozen in
time, which is exactly what a historical record needs.

## 🚀 What actually runs these files automatically — the config that matters

Every revision here is applied **without anyone typing `alembic upgrade head`**. The chain
that makes that true, in order:

1. **`Dockerfile`** — `ENTRYPOINT ["./scripts/entrypoint.sh"]`. That script, not `uvicorn`, is
   what the container runs first; `CMD ["uvicorn", ...]` is only the argument handed to it.
2. **`scripts/entrypoint.sh`** — `run_migrations()` calls exactly one command: **`alembic
   upgrade head`**. This walks the revision chain from wherever the database currently is up to
   the *newest* file in this directory, executing every `upgrade()` in order inside its own
   transaction (`transaction_per_migration=True` in `migrations/env.py`). `set -euo pipefail` at
   the top of the script is what makes this a gate, not a best-effort step: if any `CREATE TABLE`,
   `CHECK`, or `FOREIGN KEY` in a migration fails — a bad script, a constraint violated by existing
   data — the command exits non‑zero, `exec "$@"` (starting `uvicorn`) is never reached, and the
   container never comes up. **The database schema and its constraints are validated before the
   application is allowed to serve a single request.**
3. **`migrations/env.py`** — reads the connection string from `Settings.database_url_str` (never
   from `alembic.ini`, which deliberately leaves `sqlalchemy.url` blank), so the same code that
   validates production configuration is what migrations connect through.
4. **`docker-compose.yml` / orchestrator health checks** — `depends_on: condition: service_healthy`
   on Postgres delays the container from even starting `entrypoint.sh` until the database itself
   is reachable; `HEALTHCHECK ... --start-period=20s` in the `Dockerfile` gives the migration step
   room to run before the container is reported unhealthy.

This is why a revision must be correct **SQL**, not just correct Python: `alembic upgrade head` is
the one thing standing between a bad migration and a broken deploy, and it runs on every boot, on
every environment, with no human in the loop. See `app/main.py`'s `lifespan()` for why this step is
deliberately **not** done inside the FastAPI app itself (replica races), and `scripts/entrypoint.sh`
for the full rationale inline.

## Naming

`NNNN_short_description.py`, zero-padded, matching `revision`. Alembic follows
`down_revision`, not filenames — but a chronologically sortable directory is worth the convention.
